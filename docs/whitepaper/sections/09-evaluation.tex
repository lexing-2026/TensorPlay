\section{评估：可读性、正确性与开销}
\label{sec:eval}

评估从可读框架必须获得的三个轴上进行：读取的核心有多小，当训练循环改变张量时它如何精确地保护正确性，以及当每个保护和分析器探针被禁用时它的成本有多少。此外还有四个证据块来完成架构故事：填充的 CUDA/Vulkan 后端插槽 (\S\ref{subsec:eval-backends})、位于内核下方的支持核心 (\S\ref{subsec:eval-supportcores})、三轨测试套件 (\S\ref{subsec:eval-tests}) 和测量的基准数据 (\S\ref{subsec:eval-bench})。

\subsubsection{CUDA 后端（56.9\,k 行，1{,}274 次操作）}

CUDA 后端保持与 CPU 树并行的每个文件一个文件的布局，其中内核可分离：算术、逐点（2{,}154 行）、缩减、卷积（2{,}477）、索引（3{,}362），以及仅限 CUDA 的基础设施：流感知缓存分配器（1{,}288 行）、流/设备簿记、cuBLAS 句柄池、NCCL通信器缓存（418 行）、基于 Philox 的生成器和 CUDA 图形捕获。每个内核文件都以一个注册块结尾，例如\ \texttt{TENSORPLAY\_LIBRARY\_IMPL(CUDA, PointwiseKernels)}，因此每个翻译单元都是独立可迭代的。

\paragraph{分级减速引擎。} Reductions (sum, mean, min/max, Welford variance) share one code-generation template with a three-tier combine strategy: intra-warp via \texttt{\_\_shfl\_down\_sync} (no shared memory), inter-warp via shared memory within the block, and a global second-pass kernel when the tensor spans many blocks. A traits type selects the accumulation dtype per input dtype---\texttt{float} accumulation for \texttt{Half}/\texttt{BFloat16} inputs keeps precision---and per-operation functors (\texttt{SumOps}, \texttt{MeanOps}, \texttt{MinMaxOps}, \texttt{WelfordOps}) plug into the same launcher.

\begin{lstlisting}[caption={The intra-warp tier of the shared reduction template; complex numbers shuffle their two lanes because the shuffle intrinsic has no complex overload.}, label=lst:cudareduce]
__device__ inline float shfl_down(float value, uint32_t mask, int offset) {
  return __shfl_down_sync(mask, value, offset);
}
// complex has no intrinsic __shfl_down_sync overload; shuffle the
// real and imaginary lanes separately.
__device__ inline complex_t shfl_down(complex_t value,
                                       uint32_t mask, int offset) {
  float re = __shfl_down_sync(mask, value.real(), offset);
  float im = __shfl_down_sync(mask, value.imag(), offset);
  return complex_t(re, im);
}
\end{lstlisting}

\paragraph{多张量适用于优化器。} Optimizer steps act on hundreds of parameter tensors of the same dtype. The \emph{foreach} path chunks work from the whole tensor list into one grid-stride kernel (\texttt{foreach\_mta::launch}), so an Adam step updates weights, moments, and buffers in a handful of grouped launches instead of hundreds of individual ones. Eligibility is structural---same device, same dtype---and ineligible groups fall back to per-tensor launches. The CPU benchmark of \S\ref{subsec:eval-bench} (optimizer geomean 3.83$\times$) is largely attributable to this path plus fused one-kernel steps.

\paragraph{cuSOLVER 分解。} Beyond GEMM (cuBLAS, column-major staging via \texttt{clone\_batched\_column\_major}), the backend wraps cuSOLVER for SVD, Cholesky, and LU with device-side info pointers so positive-definiteness failures surface as exceptions rather than silent garbage.

RNG 故事的一半是捕获意识。内核从 Philox 计数器中抽取随机数，并且在图形捕获期间，计数器无法烘焙到内核启动中 - 每次重播都必须看到随机流的新切片。因此，生成器暴露了两种状态：

\begin{lstlisting}[caption={Philox counter reservation, in two regimes: eager launches get plain (seed, offset); captured kernels read them from device buffers that a replay prologue refreshes.}, label=lst:philox]
// Atomically reserves `increment` philox counter values for the current
// device and returns the (seed, offset) the launching kernel should consume.
P10_API std::pair<uint64_t, uint64_t> philox_engine_inputs(uint64_t increment);

// graph capture kernels consume the plain (seed, offset) values; while a
// capture is underway they instead read seed/offset from device buffers owned
// by the capturing graph plus a per-kernel intragraph offset, so replay
// prologues can refresh the buffers and every replay consumes a fresh slice
// of the random stream instead of repeating capture-time values.
P10_API PhiloxCudaState philox_cuda_state(uint64_t increment);
\end{lstlisting}

\subsubsection{Vulkan 后端（16.3\,k C++ + 4.5\,k GLSL，145 个操作）}

Vulkan 是最小的完整后端，这正是它的教学价值：它演示了三个后端密钥中的插槽 2 接受具有 \emph{no dispatcher change} 的新设备系列。布局分为三层：

\begin{itemize}[leftmargin=1.2em]
\item \texttt{api} 层（29 个文件）：原始句柄上的精简对象模型---\texttt{Adapter}（设备选择）、\texttt{Context}、\texttt{Resource}（具有 VMA 的缓冲区/图像）、\texttt{Pipeline}、\texttt{Command}、\texttt{QueryPool}、\texttt{vTensor}（后端的张量视图）。
\item 一个 \texttt{ops} 层（34 个文件）：145 个 \texttt{m.impl} 注册，每个文件一个结束 \texttt{TENSORPLAY\_LIBRARY\_IMPL(Vulkan,...)} 块（总共 26 个块）。内核通过注册表查找 \texttt{VK\_KERNEL(name)} 按名称获取着色器。
\item \texttt{glsl} 层（70 个模板文件）：使用迷你预处理器（\texttt{\->if}/\texttt{\->else} 块）计算着色器，由 63 个变量表条目驱动。
\end{itemize}

构建管道已完全生成：418 行 Python 阶段预处理每个模板，为 Vulkan 1.0 SPIR-V 调用 \texttt{glslangValidator}，解析描述符集绑定，并发出嵌入式 C++ 注册表；构建规则连接依赖项，因此编辑任何着色器或变体表都会重新嵌入所有 220 个已编译的 \texttt{.spv} 变体。量化系列在这里是一等公民（量化卷积、每张量反量化、\dots），这就是为什么 Vulkan 提供量化内核，而 CPU 保持 Python FakeQuantize 层（\S\ref{subsec:eval-trimmed}）的量化。

matmul 内核将整个分层展示在一个主体中——验证、分配设备张量、打包布局、绑定制服、提交：

\subsection{AMD 可移植性：Hipify 构建路径}
\label{subsec:eval-rocm}

除了三个一流的后端之外，TensorPlay 还通过其 CUDA 源的自动转换而不是维护的分支在 AMD GPU 上运行。在配置时，构建脚本将每个 CUDA 源和绑定到单独的树中，并应用正则表达式重写 ---\texttt{cudaMalloc} 变为 \texttt{hipMalloc}，内核启动变为 \texttt{hipLaunchKernelGGL} --- 之后，使用 HIP 工具链编译分阶段树。两个构建选项强制 CUDA 和 ROCm 路径之间的互斥，因为两者都注册相同的设备和调度槽；然后调度程序透明地路由到翻译后的内核。设计教训：当后端仅在词汇方面有所不同时，请在构建时翻译词汇并保留一个语义源，而不是种植一棵手动维护的漂移的兄弟树。

\subsection{数值稳定性：CPU 上的级联求和}
\label{subsec:eval-cascadesum}

当使用单个累加器时，长浮点和会在元素计数中线性累积舍入误差。 CPU 缩减路径改为实现 \emph{cascade} 方案：部分和保存在一个小的级别数组中，并且每当其索引达到二次幂时，一个级别就会刷新到下一个级别。错误增长从 $O(n)$ 下降到 $O(\log n)$，因为每个级别仅增加可比较数量级的数字。

\begin{lstlisting}[caption={The cascade accumulator: four levels, flushed on a power-of-two cadence; vector loads feed every lane in parallel.}, label=lst:cascadesum]
constexpr int64_t levels = 4;
const int64_t level_power = std::max<int64_t>(4, ceil_log2(size) / levels);
const int64_t level_step  = int64_t(1) << level_power;
const int64_t level_mask  = level_step - 1;
std::array<std::array<T, N>, levels> acc{};   // one accumulator per lane
for (; i + level_step <= size;) {
  /* load N-wide vector, add into level 0 */
  if ((i & level_mask) == 0) {                // cadence hit: flush upward
    for (int64_t l = 0; l + 1 < levels; ++l) {
      /* acc[l+1] += acc[l]; acc[l] = 0; */
    }
  }
}
\end{lstlisting}

\texttt{normsq}（平方和）的 AVX-512 快速路径融合了 FMA 指令的乘法和累加；在兼容硬件上，这是图~\ref{fig:benchhist}中记录的$9.9\times$ \texttt{norm2}加速背后的机制，其中参考的标量循环不能使用相同的指令混合。

\subsection{分布式训练：FSDP、DTensor、Functional Collective}
\label{subsec:eval-distributed}

分布式堆栈（63\,k 个 Python 行加上 17\,k 个基于 gloo 和 MPI 的进程组后端 C++ 行）组织成三层，反映了支柱理念：C++ 通信层、可微分的 Python 功能层和可组合的分片策略。

\paragraph{FSDP。} Fully sharded data parallelism is configured by a small enum vocabulary rather than ad-hoc flags: \texttt{FULL\_SHARD} (parameters sharded, gathered per layer, freed after use), \texttt{SHARD\_GRAD\_OP} (gather once per forward, shard only gradients and optimizer state), \texttt{NO\_SHARD} (plain DDP), and a hybrid intra/inter-node variant. Policies compose as dataclasses---\texttt{MixedPrecision} chooses independent dtypes for parameters, reduction, and buffers; \texttt{CPUOffload} swaps parameters to host memory between uses; \texttt{BackwardPrefetch} overlaps the next layer's gather with the current layer's backward.

\begin{lstlisting}[caption={The strategy and policy vocabulary of FSDP: everything the sharding engine needs is one enum plus three small dataclasses.}, label=lst:fsdpvocab]
class ShardingStrategy(Enum):
    FULL_SHARD    = auto()   # params sharded, gathered per-layer
    SHARD_GRAD_OP = auto()  # params gathered once; grads+state sharded
    NO_SHARD      = auto()   # plain DDP
    HYBRID_SHARD  = auto()   # replicate intra-node, shard inter-node

@dataclass
class MixedPrecision:
    param_dtype: Any = None     # computation dtype
    reduce_dtype: Any = None    # all-reduce dtype
    buffer_dtype: Any = None    # communication buffers

@dataclass
class CPUOffload:
    offload_params: bool = False
\end{lstlisting}

\paragraph{D 张量。} Sharded tensors are described by a \emph{placement} algebra over a device mesh: \texttt{Shard(dim)} splits along a dimension, \texttt{Replicate} copies, and \texttt{Partial(reduce\_op)} holds partial values that reduce to the global tensor. Operations on a \texttt{DTensor} dispatch through a sharding-aware layer that inserts the minimal set of collectives (\texttt{all\_gather}, \texttt{reduce\_scatter}) needed to satisfy the output placement---the same redispatch idea as \S\ref{sec:redispatch}, lifted from backends to topologies.

\paragraph{具有 autograd 功能的集体。} Each collective is exposed twice: a plain function and an autograd-aware variant built as a differentiable \texttt{Function}, so distributed operations compose inside the ordinary DAG. Communication overlaps computation through a lazy tensor wrapper:

    """Tensor storage with a pending collective completion handle."""
    def __new__(cls, elem, work=None):
        if isinstance(elem, AsyncCollectiveTensor):
            return elem            # already lazy; keep the single handle
        return _attach_async(elem, work)
    def trigger_wait(self, timeout=None):
        ...                        # waits once, then demotes to plain Tensor
        self.__class__ = tp.Tensor
\end{lstlisting}

\subsection{序列化：.mega 格式和安全互操作}
\label{subsec:eval-serialization}

模型持久性既是一个安全问题，也是一个存储问题。 TensorPlay 的本机格式是一个二进制容器，具有四字节魔法、标记元数据记录（整数、浮点数、字符串、嵌套数组）、存储重复数据删除、每个有效负载 CRC32 或 SHA256 摘要以及默认的 4\,096 字节对齐，因此有效负载可以是 \texttt{mmap}-ed 零复制。加载是基于白名单的端到端：没有pickle，没有嵌入代码，永远。

互操作性遵循相同的原则。 \texttt{safetensors} 文件通过其 JSON 标头格式进行读写。来自其他框架的传统基于 zip 的检查点由专用的 unpickler 进行解析，其全局变量严格列入张量重建函数的允许名单；存储类型通过固定表映射到本机数据类型，并且允许列表之外的任何内容都会引发而不是执行。位置处理 (\texttt{map\_location}) 接受设备字符串、设备到设备映射或接收存储存根的可调用函数。集线器实用程序完成生命周期：在可配置根目录下缓存下载、哈希验证、恢复支持和完成时原子重命名。

\paragraph{操作内池。} The pool is created once and reused: the thread count moves through a \texttt{NOT\_SET $\rightarrow$ value $\rightarrow$ CONSUMED} atomic state machine so the first \texttt{set\_num\_threads} freezes the pool size, and \texttt{in\_parallel\_region} is answered from \texttt{thread\_local} flags instead of a mutex + thread-id scan. Kernels enter via a header template with a grain size; the C bridge exposes the same pool to oneDNN's partitioning.

\begin{lstlisting}[caption={The whole pool is one class: spawn workers once, drain on shutdown.}, label=lst:pool]
class IntraopThreadPool {
 public:
  explicit IntraopThreadPool(int num_workers) {
    for (int i = 0; i < num_workers; ++i) {
      threads_.emplace_back([this] { worker_loop(); });
    }
  }
  IntraopThreadPool(const IntraopThreadPool&) = delete;
  IntraopThreadPool& operator=(const IntraopThreadPool&) = delete;
  ~IntraopThreadPool() {
    {
      std::unique_lock<std::mutex> lk(mutex_);
      running_ = false;
      condition_.notify_all();
    }
    for (auto& t : threads_) t.join();
  }
  /* ... */
\end{lstlisting}

专用线束根据经验验证这两个属性：1 元素添加上的 8 线程/1 线程比率为 0.94$\times$（目标 $\le$1.5$\times$：超额订阅不会损害小型操作），4M 元素添加上的 8 线程/1 线程比率为 0.99$\times$（有工作时会启用并行性）。

\paragraph{oneDNN 和 MKL。} The oneDNN context holds one engine per process and, critically, drives oneDNN \emph{outside} its own callbacks: primitive partitioning is bridged onto the intra-op pool so nested parallelism cannot deadlock. CPU kernels call oneDNN eltwise primitives directly for tanh/relu-family activations, while matmul goes to MKL via \texttt{cblas\_sgemm} behind the \texttt{USE\_MKL} guard. This is the whole vendor-acceleration story of TensorPlay: two narrow bridges, no vendor data structures in the object model.

\paragraph{RNG.} CPU generators wrap a self-contained MT19937 so the distribution layer consumes raw engine words (the C++ standard's \texttt{std::distributions} are implementation-defined and therefore unusable for reproducibility):

对图~\ref{fig:benchhist}的三读对于论文的主张很重要。首先，\emph{both} 方面的分布很广：可读性优先的框架并不是一律较慢；在元素和归约系列上，手写矢量化内核获胜（1M 时为 exp 2.4$\times$、gelu 2.3$\times$；8M 时为 4.8$\times$/4.3$\times$），而融合多内核路径 (gelu-tanh)、小批量 \texttt{bmm} 和 \texttt{cumsum} 则落后。其次，胜利和失败按内核文件进行聚类，这正是可读性的承诺：逐点内核文件是读取解释两个尾部的单个文件。第三，matmul 具有参考竞争性（1K$^3$ 0.94$\times$，高瘦 1.8$\times$），因为两个框架都位于相同的 MKL \texttt{cblas\_sgemm} 中——调度程序添加了在 \S\ref{subsec:eval-microbench} 中测量的相同的低于 1% 的条子。

基准树还包含更重的端到端工具：一个 1{,}489 行 ResNet-18 脚本，运行 10 轮训练竞赛，加上需要 \texttt{allclose} logits 和相同的 top-1 预测的严格状态字典传输，以及需要 GPU 的 CUDA 图形重放工具。它们的 CUDA 门控部件与测试树具有相同的环境防护。

因此，调度表是 \texttt{array<atomic<KernelFunction>,13>}，每个槽宽松初始化为 \texttt{nullptr} 并使用 \texttt{memory\_order\_release} 发布。键集是 13 个键的 \texttt{uint32\_t} 位集；优先级解析扫描掩码中数值最大的位，因此优先级为 \texttt{Vmap -> Autocast -> Autograd -> backend}。助手一次清除一个轴，由每一层下面的重新调度使用。

\begin{lstlisting}[caption={The \texttt{Composite} fallthrough in the hot path: one extra load, only when a backend slot is empty.}, label=lst:composite]
KernelFunction getKernel(DispatchKey key) const noexcept {
  auto k = table_->kernels[dispatchKeyIndex(key)].load(acquire);
  if (!k && is_backend_key(key)) {
    constexpr auto kCompositeIdx = dispatchKeyIndex(Composite);
    k = table_->kernels[kCompositeIdx].load(acquire);   // one extra load
  }
  return k;
}
\end{lstlisting}

TensorPlay 保留一组紧凑的调度键，并将专用轴保留在核心表之外。没有 \texttt{Meta} 键，也没有开放的注册 API：注册是一个由一个互斥锁保护的封闭式 \texttt{unordered\_map<string,DispatchTable>}，并且 \texttt{TENSORPLAY\_LIBRARY\_IMPL} 宏扩展为进程生命周期静态构造函数。代价是纯形状推理、稀疏调度和量化调度没有专用的快速路径；它们要么共享 \texttt{Composite} 后备，要么明确不受支持。

\subsection{Autograd 节点：148 个生成、显式 DAG、无磁带}
\label{subsec:eval-autograd-nodes}

生成器通过表达式 AST 解析导数公式注册表（分组后 345 个原始记录分解为 187 个公式）并发出 148 个节点结构。每个节点将保存的前向张量存储为 \texttt{SavedVariable} ，其中公式需要它们，并从决定保存集的同一 AST 合成 \texttt{apply} ，因此保存列表、构造函数和 \texttt{apply} 不会漂移。公式无法表达的手写节点（串联、堆叠、滚动）遵循相同的 \texttt{SavedVariable} 契约。

没有磁带。该图是每个节点的 \texttt{next\_edges} 的传递闭包，其中每个 \texttt{Edge} 仅携带提示——形状提示、梯度数据类型、设备提示——因此向后可以在不接触前向张量的情况下实现缺失的梯度。 \texttt{GraphTask} 保存每次向后构建一次的依赖计数器映射、由原始 \texttt{Node*} 键控的输入缓冲区映射以及 \texttt{grad} 捕获的输出向量。 \texttt{ReadyQueue} 是按节点的创建序列号排序的最大堆：它首先弹出最大的序列号，近似于反向创建顺序，而真正的拓扑顺序由依赖计数器强制执行。每个节点解释器执行十个步骤——梯度模式保护、捕获簿记、缺失梯度物化、预钩子、评估节点保护、\texttt{apply}、后钩子、\texttt{sum\_to\_shape}、dtype 转换、NaN 探测——然后在任务互斥体下传播到父级。

内存/性能权衡是明确的：每条边都保存一个 \texttt{shared\_ptr<Node>}，每个输入缓冲区保存一个 \texttt{vector<Tensor>}，因此每个节点一个 \texttt{shared\_ptr} 加上每个不同输入槽的一个分配。生产运行时使用 \texttt{intrusive\_ptr} 来削减控制块。 TensorPlay 保留标准库指针，以便学生可以使用普通工具跟踪所有权；常数因子成本是一个教学决策，如此记录。

\subsubsection{版本保护：\texttt{SavedVariable}}

后向所需的前向张量不直接存储。 \texttt{save} 将张量的版本计数器复制到保存的变量中； \texttt{unpack} 重新加载当前版本并引发分歧：

\begin{lstlisting}[caption={Version mismatch is loud: the message spells both versions.}, label=lst:savedvar-eval]
TP_THROW(RuntimeError,
  "one of the variables needed for gradient computation has been modified "
  "by an inplace operation: [saved version: " + to_string(saved_version_) +
  "; current version: " + to_string(current) + "]");
\end{lstlisting}

版本计数器是在每个就地操作上碰撞的 \texttt{atomic<uint32\_t>} （由“不处于推理模式”保护），并在基础及其视图之间急切地共享，因此改变视图也会碰撞基础的计数器。生成的节点将每个张量成员存储为 \texttt{SavedVariable} 并解压 \texttt{apply} 的顶部；手写节点也做同样的事情。当不需要保留图时，引擎会释放保存的变量以提前释放内存。

\subsubsection{形状和数据类型保护：\texttt{sum\_to\_shape}}

正向期间的广播会将标量梯度膨胀到输出形状。在下一个边缘消耗它之前，引擎会减少它：

\begin{lstlisting}[caption={Broadcast recovery: reduce the leading dims and the size-1 broadcast dims, then reshape.}, label=lst:sumtoshape-eval]
static Tensor sum_to_shape(const Tensor& grad, const vector<int64_t>& target){
  if(target.empty()) return ops::sum(grad);                 // scalar ()
  int64_t leading = (int64_t)grad.dim() - (int64_t)target.size();
  if(leading < 0){ /* reshape up when numel matches, else passthrough */ }
  vector<int64_t> reduce; for(int64_t i=0;i<leading;++i) reduce.push_back(i);
  for(int64_t i=leading;i<(int64_t)grad.dim();++i)
    if(target[i-leading]==1 && grad.size(i)!=1) reduce.push_back(i);
  Tensor cur = reduce.empty()? grad : ops::sum(grad,reduce,true);
  if(leading>0) cur = ops::reshape(cur,target); return cur;
}
\end{lstlisting}

记录的形状来自边的形状提示（与标量形状 \texttt{} 区分开的“无提示”），数据类型来自边的数据类型提示。 dtype 与提示不一致的浮点 grad 会被强制转换——自动转换情况： \texttt{fp32} grad 重新输入低精度向后。两个操作都在每个节点的梯度模式保护下运行，因此当 \texttt{create\_graph} 为 true 时，二阶梯度仍然构建一个图。

\subsubsection{设备保护：\texttt{DeviceMismatchError}}

推理张量永远不会获取自动微分密钥：它们的版本计数器被创建为禁用，因此密钥计算会产生裸露的后端位。不匹配的设备不会被静默复制；他们抛出一个独特的Python类型：

\begin{lstlisting}[caption={A distinct exception for device mismatch, derived from the runtime-error base.}, label=lst:devicemismatch]
class P10_API DeviceMismatchError : public RuntimeError {
  using RuntimeError::RuntimeError;
};
\end{lstlisting}

该 throw 会在元素方式和 matmul 入口点以及归约迭代器中的设备不一致时触发。因为该类型派生自 \texttt{RuntimeError}，所以它携带源位置和可选的 C++ 堆栈，但 Python 可以将其与其他运行时错误分开捕获。

\subsubsection{异常守卫：\texttt{AnomalyMode}}

启用异常模式会设置两个对每个线程可见的进程全局标志：记录创建堆栈和检查 NaN。在节点创建时，模式存储当前堆栈（默认情况下为 C++ 帧；Python 绑定在 GIL 下安装 \texttt{traceback.format\_stack}），并且如果当前正在评估向后节点，则将评估节点记录为父节点。在向后过程中，引擎将评估节点推送到线程本地防护上，因此在 \texttt{apply} 内创建的任何节点都会记录其父节点。出现异常时，引擎会在重新抛出之前打印前向堆栈链。 NaN 探针是

\begin{lstlisting}[caption={The NaN probe runs under a disabled grad-mode guard so it never records history.}, label=lst:nanprobe-eval]
bool tensor_has_nan(const Tensor& t){
  if(!t.defined() || !isFloatingOrComplexType(t.dtype())) return false;
  return t.ne(t).any().item<bool>(); // ieee NaN != NaN via dispatch
}
\end{lstlisting}

链打印机遍历记录的父指针（每个 \texttt{weak\_ptr<Node>}），为每个父节点打印“先前的计算是由 \dots 引起的”，直到过期，因此 \texttt{create\_graph} 故障显示导致失败的后向节点的前向站点。

\subsection{禁用时的开销}
\label{subsec:eval-overhead}

可读框架是根据开发人员不注意时的成本来判断的。每个操作上都有三个热路径：分析器门、自动微分模式门和调度密钥计算。这三个分支都被设计为预测不被采用或成为一对分支。

\midrule

\subsubsection{分析器：2 个周期}

探查器门是一个 \texttt{memory\_order\_acquire} 负载，内联到 x86 上的 \texttt{mov} + \texttt{cmp} + 预测未采用的分支。形状和位点捕获都会增加一个额外的 \texttt{acquire} 负载，但它们严格位于门的真实分支内，因此在禁用时它们会添加零周期。仅 CPU 会话根本不会装备 GPU 计时器：绑定在第一个操作之前使用 \texttt{release} 存储计时标志，并且 GPU 计时器路径在解除装备时提前返回。对于一个负载，在 3.5GHz 时测得的基线开销为 $\sim$0.6ns；请参阅 \S\ref{sec:profiler} 了解启用的成本（30\,ns CPU，80--120\,ns 形状，两个 \texttt{cudaEventRecord} 在 $\sim$5\,\textmu s）。

\subsubsection{\texttt{GradMode} / \texttt{InferenceMode}: \texttt{thread\_local}}

两种模式都是 \texttt{thread\_local bool}s（\texttt{GradMode} 默认为 true，\texttt{InferenceMode} 默认为 false）。每个生成的包装器将 \texttt{requires\_grad} 计算为 \texttt{grad\_mode \&\& !inference\_mode \&\& any\_input\_requires\_grad}---三个带短路的内联负载。工作线程通过在节点评估期间覆盖 TLS 的保护来遵守任务的 \texttt{create\_graph} ，因此禁用的成本正是引擎无论如何都会支付的 TLS 负载。推理张量还跳过版本计数器分配。

\subsubsection{调度员：2个分支机构}

\begin{lstlisting}[caption={Autocast exclusion is one predicted branch; composite fallthrough is the second.}, label=lst:dispbranch]
if (is_autocast_key(key) && !autocast::is_enabled(key)) [[unlikely]]
  TP_THROW(NotImplementedError, ...);
auto kernel = handle.getKernel(key);   // slot load; composite if empty
if (!kernel) TP_THROW(NotImplementedError, ...);
\end{lstlisting}

第一个分支是上面的自动转换排除；第二个位于 \texttt{getKernel} 内：索引槽的 1 个 \texttt{acquire} 负载加上（仅当后端槽为空时） \texttt{Composite} 槽的 1 个额外 \texttt{acquire} 负载。对于任何具有本机内核的操作，不会采用复合负载。 Codegen 提升了 \texttt{static const OperatorHandle} ，因此每个进程都会解析一次名称查找。

两种构建时间选择可以摊销冷成本。 Python 扩展被编译为一个统一构建翻译单元（9{,}300 行生成的绑定标头加上绑定单元在一起），而 \texttt{p10} 故意选择退出统一：内核翻译单元必须针对每个文件静态注册保持独立。 shim 库 \texttt{tp\_python} 只是重新导出真实符号，使导入时间由 \texttt{dlopen} 而不是 Python 开销主导。

显式 DAG 的教学权衡是每个节点一个 \texttt{shared\_ptr} 与 \texttt{intrusive\_ptr}。生产运行时使用侵入式引用计数来避免每个节点有单独的控制块； TensorPlay 保留了标准控制块，因此在 \texttt{gdb} 和 \texttt{valgrind} 中可以观察到所有权，而无需自定义漂亮的打印机。因此，持续吞吐量在后向节点分配中会出现常数因子开销，该开销与张量大小无关，并且在内核时间占主导地位的大型矩阵相乘上不可见。

以下是两个结论。首先，\textbf{the dispatcher is not the bottleneck}； C++ 端调度是 $\sim$890\,ns 总计 ($<0.5\%$) 的 $\sim$4\,ns，因此 13 槽数组和封闭密钥设计在 Python 层中实际上不会花费任何成本。其次，\textbf{the binding dominates}，它是每操作 Python 控制流所固有的：将 1{,}000 个操作批处理到已编译的 \texttt{stax} 程序中的训练步骤将 1{,}000 个桥交叉替换为一个 (\S\ref{sec:arch:stax})，从而消除了该主机上每个步骤 $\sim$0.9\,ms 的纯每操作开销。

\subsubsection{CPU vs.\ CUDA vs.\ Vulkan 调度开销}

三个后端共享一张调度表（\S\ref{sec:redispatch}）；只有终端内核不同。上面测得的 CPU 数量适用于 \texttt{CPU}=slot 0。CUDA 添加了流推送以及（如果进行分析）\texttt{cudaEventRecord}； Vulkan 添加了命令缓冲区提交。后端增量遵循内核条目结构：CUDA 操作支付相同的 $\sim$4\,ns 调度加上驱动程序启动常量（$\sim$5--10\,\textmu s 主机端，与分析器的 \texttt{cudaEventRecord} 对相同的顺序）； Vulkan op 支付调度费用加上 \texttt{vkQueueSubmit} ($\sim$10--30\,\textmu s)。对于所有三个后端，调度程序自己的贡献是相同的 1\% 条子，这是设计目标：后端选择改变内核，而不是调度路径。

\begin{itemize}[leftmargin=1.2em]
\item \textbf{No third-party keys.} 注册已结束；没有 \texttt{registerDispatchKey} ，也没有每个操作符的盒装内核堆栈。好处是名称查找是一个哈希探针加一个原子负载，而不是向量遍历。
\item \textbf{No meta dispatch.} 生产 \texttt{Meta} 键运行仅计算输出形状和数据类型的内核。 TensorPlay 从不调度元内核；编译器支柱的形状传播是普通的 Python，具有形状属性传递、死代码消除和常量折叠。因此，调度程序没有 \texttt{Meta} 槽，也没有“元张量”概念。
\item \textbf{No sparse/quantized axes.} 稀疏布局是最小存储有效负载（具有 CSR 变体的 COO），而不是调度轴。量化仿射 int8 在 CPU 上作为 Python FakeQuantize 直通估计器运行，而不是作为 dtype$\times$key 调度 — 尽管 Vulkan 后端提供真正的量化着色器 (\S\ref{subsec:eval-backends})。没有 \texttt{SparseCPU} 或 \texttt{QuantizedCPU} 键。
\item \textbf{Teaching compiler.} Fusion 正是一种模式 ---\texttt{mul}$\rightarrow$\texttt{add}--- 加上带有 CPU 矢量化的逐点表达式程序。图执行器通过基于生命周期的缓冲区回收按顺序进行解释；没有循环或 CUDA 的代码生成，没有缓冲区重用规划，也没有性能模型。它是一个概念演示，而不是生产编译器。
\item \textbf{Composite fallbacks.} 修剪后的轴不是悬崖：当后端插槽为空时，两打复合注册（查看/复制、直方图、唯一、itertools、积分、张量属性）用作中性内核。添加本机内核可以单独替换该操作的后备。
\end{itemize}
