\section{TensorIterator: Broadcast, Type Promotion, and Parallel Reduction}
\label{sec:tensoriterator}

\subsection{Problem: One-Iteration Abstraction}

A pointwise \ac{cpu} kernel for \texttt{add} must handle three orthogonal concerns: (i) broadcast, (ii) type promotion, and (iii) non-contiguous strides. Hand-writing four nested loops per kernel would duplicate 80\% of. TensorIterator is the reusable execution template: kernels provide only \texttt{dst[i]=func(src[i])}.

The CPU implementation provides the complete reusable iterator path, while CUDA kernels currently hand-write indexing; unifying the two paths remains future work.

\begin{tpdef}[Definition (TensorIterator)]
The \emph{TensorIterator} is a reusable execution template for elementwise and reduction kernels. Given operands $(t_1,\dots,t_n)$ and an output $o$, its build pipeline (seven steps, \S\ref{sec:tensoriterator}) computes a common shape $S$, a common dtype $D$, and per-operand strides such that the innermost loop can execute with unit stride on the contiguous path. A kernel then supplies only a scalar functor $\mathrm{dst}[i] = f(\mathrm{src}_1[i],\dots,\mathrm{src}_n[i])$ plus an optional vectorized variant; broadcast, promotion, and stride reordering are all resolved \emph{before} the loop runs, so the hot path contains no per-element branching on those concerns.
\end{tpdef}

\subsection{Build Pipeline: Seven Steps}

:

\begin{lstlisting}[caption={seven steps.}, label=lst:tibuild]
void TensorIteratorBase::build(Config& cfg){
  is_reduction_=cfg.is_reduction_;
  populate_operands(cfg); mark_outputs(); compute_mem_overlaps(cfg);
  compute_shape(cfg); mark_resize_outputs(cfg); compute_types(cfg);
  if(!fast_set_up(cfg)){ compute_strides(cfg); reorder_dimensions(); allocate_or_resize_outputs(); coalesce_dimensions(); }
  for(auto& op: operands_) op.data = op.tensor().data_ptr();
}
\end{lstlisting}

\begin{enumerate}[leftmargin=1.2em]
\item \textbf{populate\_operands:} move \texttt{Tensor} into \texttt{OperandInfo}, record \texttt{data} and \texttt{stride\_bytes}.
\item \textbf{compute\_shape}: broadcast rule \texttt{size==1} broadcasts, else equal; preserves \texttt{0}-size.
\item \textbf{compute\_types} ( folds \texttt{promoteTypes},): if \texttt{promote\_inputs\_to\_common\_dtype}, creates temporaries via \texttt{op.tensor.to(common\_dtype)}; if \texttt{cast\_common\_dtype\_to\_outputs}, allocates temp output.
\item \textbf{compute\_strides + reorder\_dimensions:106}: insertion sort dims by stride ascending, reduced dims front; disabled if \texttt{enforce\_linear\_iteration}.
\item \textbf{coalesce\_dimensions:530}: merges \texttt{shape[n]*stride[n]==stride[n+1]} adjacent dims.
\item \textbf{allocate\_or\_resize\_outputs}: \texttt{empty(shape, dtype, device)} if \texttt{resize\_outputs}.
\item \textbf{post:} fill \texttt{op.data = tensor.data\_ptr}.
\end{enumerate}

 collapses to \texttt{shape[0]=numel} when all operands share shape and are contiguous.

\subsection{Type Promotion Lattice}

 defines a strict lattice:

\begin{lstlisting}[caption={lattice (abridged).}, label=lst:promote]
DType promoteTypes(DType a,DType b){
  if(a==b) return a; if(a==Undefined||b==Undefined) return Undefined;
  if(isComplexType(a)||isComplexType(b)){
    if(a==ComplexDouble||b==ComplexDouble) return ComplexDouble;
    if(a==ComplexFloat||b==ComplexFloat) return isFloatingType(other)? ComplexDouble: ComplexFloat;
  }
  if(isFloatingType(a)||isFloatingType(b)){
    if(a==Float64||b==Float64) return Float64; if(a==Float32||b==Float32) return Float32;
    if(a==Float16 && b==BFloat16) return Float32; // avoid mutual loss
  }
  if(a==Bool) return b; if(b==Bool) return a;
  if(a==Int64||b==Int64) return Int64;
}
\end{lstlisting}

 enumerates 20+ types (\texttt{UInt8}, \texttt{Float32}, \texttt{BFloat16}, \texttt{ComplexDouble}, \texttt{QInt8},...), with \texttt{isComplex} predicates and \texttt{elementSize}. The result is written to \texttt{Edge::grad\_dtype} for backward cast-back.

\subsection{Parallel and Reduction}

 \texttt{for\_each(loop, grain=GRAIN\_SIZE)} dispatches to \texttt{parallel::parallel\_for} (custom thread pool, \texttt{GRAIN\_SIZE=32768}). \texttt{parallel\_reduce} selects \texttt{two\_pass\_reduction} for single-element outputs (per-thread buffer then \texttt{final\_reduce}) vs.\ (\texttt{find\_split\_dim}, \texttt{narrow}, \texttt{foreach}).

\subsection{Kernel Wiring}

:

\begin{lstlisting}[caption={Pointwise wiring.}, label=lst:pointwise]
template<Func> Tensor unary_op_kernel(const Tensor& self, Func func, VOp vec){
  Tensor out = empty(shape,dtype,device); Tensor contig=self.contiguous();
  bool vec_ok = vecunary::vec_ready() && vec!=None && (dtype==Float32||Float64);
  switch(dtype){ case Float32: { auto s=contig.data_ptr<float>(); auto d=out.data_ptr<float>();
    if(vec_ok) parallel_for(0,n,8192, [&](b,e){ vec_run(vec,prm,s,d,b,e); });
    else parallel_for(0,n,8192,[&](b,e){ for(i=b;i<e;i++) d[i]=func(s[i]); }); break; } ... }
  return out;
}
\end{lstlisting}

\subsection{Design Trade-offs}
\label{sec:ti:tradeoffs}

\textbf{Resolve-before-loop vs.\ per-element branching.} The iterator could check broadcast/promotion inside the inner loop instead of precomputing shapes, types, and reordered strides in the seven-step build. Rejected: per-element branching on concerns that are loop-invariant wastes a compare and a predictable-not-taken slot on every element; resolving up front (\S\ref{sec:tensoriterator}) puts the whole cost in setup, so the hot loop is a bare unit-stride \texttt{dst[i]=func(src[i])} that autovectorizes. The trade: a broadcast \texttt{[3,1,5]+[4,5]} pays $\sim$1\,\textmu s of setup per op call, amortized only over enough elements---which is why very small tensors ($<$16 elements) take a dedicated fast path that skips the full iterator build.

\textbf{TI on CPU only vs.\ both backends.} Extending TI to CUDA (Table~\ref{tab:ti_compare}) would unify the two kernel families. Deferred, not rejected: CUDA TI needs a device-side iterator state layout and different parallelization decisions (grid-stride vs.\ grain 8192), and the hand-written CUDA kernels at \texttt{PointwiseKernels.cu} are correct today. The seam is documented so the unification is a refactor, not a redesign.
