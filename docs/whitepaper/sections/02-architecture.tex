\section{Four-Pillar Decomposition}
\label{sec:arch}

The framework is partitioned into four physically isolated shared libraries plus one Python extension, all produced from a single CMake invocation. Isolation is not editorial; it is enforced by directory, target, link edge, and header visibility. A newcomer reads \path{p10} to understand tensor storage without learning any differentiation concept; a kernel author rebuilds only \path{p10} after touching an arithmetic kernel; a compiler author experiments inside \path{stax} without relinking the storage layer. The cost is explicit boundaries and the absence of whole-program inlining, which this project accepts.

\subsection{Build Order and the Audited Move}
\label{sec:arch:buildorder}

\path{CMakeLists.txt:938--945} declares the order in exactly four lines:

\begin{lstlisting}[caption={\path{CMakeLists.txt:938--945} --- pillar order is load-bearing.}, label=lst:buildorder]
# Add p10
add_subdirectory(p10)          # :938
# Add tpx
add_subdirectory(tpx)          # :941
# Add stax (Optional)
add_subdirectory(stax)         # :944
\end{lstlisting}

\path{tpx/CMakeLists.txt:26} links \path{p10} privately; \path{tpx/CMakeLists.txt:40} re-exports it publicly so consumers that depend on \path{tpx} automatically get the p10 interface. \path{stax/CMakeLists.txt:8} links both \path{p10} and \path{tpx} privately and re-exports \path{p10} publicly at line~17. \path{CMakeLists.txt:1108} links \path{_C} against \path{p10 tpx stax tp\_python}: this is the only place where the three levels meet. Reordering any of these three \texttt{add\_subdirectory} calls or adding a back edge immediately fails with a CMake configure error or an undefined reference at link time, not a silent runtime mis-order.

The generate step precedes all of this. At \path{CMakeLists.txt:308--344} a \texttt{custom\_command} generates ten artifacts under \path{build/generated/tensorplay/ops/} from \path{config/native\_functions.yaml} and \path{config/derivatives.yaml} via \path{tools/codegen/main.py}. Every pillar target declares \path{add\_dependencies(generate\_code)} (e.g.\ \path{p10/CMakeLists.txt:486}, \path{tpx/CMakeLists.txt:25}). The generated header is mixed into \path{p10/include/Tensor.h:329} via \path{\#include "tensorplay/ops/TensorGenerated.h"}; the generated source is appended to \texttt{P10\_SOURCES} at \path{p10/CMakeLists.txt:144} as \texttt{\$\{GEN\_CPP\}}. Thus a YAML edit rebuilds only the changed generated file plus its dependents.

\path{p10/CMakeLists.txt:28} retains a single commented line:

\begin{lstlisting}[caption={\path{p10/CMakeLists.txt:28} --- audit trail, not dead code.}, label=lst:audittrail]
    # src/AutogradMetaInterface.cpp (Moved to TPX)
\end{lstlisting}

This is intentional. An earlier revision implemented the concrete metadata inside \path{p10}; the current design keeps \path{p10} header-free of \path{tpx} so the USB slot at \path{p10/include/AutogradMetaBase.h:13} suffices. Leaving the comment in the source list records the decision boundary: grepping the comment proves the file once lived in \path{p10} and was deliberately vacated to preserve acyclicity. Deleting it would erase the history of why \path{p10} must not include \path{tpx}; resurrecting it inside \path{p10} would reintroduce a back edge and break the invariant checked by \path{grep -rn "tpx" p10/include/} which must return empty.

A related discipline appears at \path{CMakeLists.txt:930--936}. On Windows where \texttt{BUILD\_SHARED\_LIBS} is normally \texttt{ON} for Linux wheels, the block forces \path{BUILD\_SHARED\_LIBS OFF}:

\begin{lstlisting}[caption={\path{CMakeLists.txt:934--936} --- Windows static embedding.}, label=lst:winstatic]
if(WIN32 AND BUILD_SHARED_LIBS)
    set(BUILD_SHARED_LIBS OFF)
endif()
\end{lstlisting}

Without the switch, each DLL would require \path{\_\_declspec(dllexport)} on every p10 symbol crossing the boundary, which the codebase does not carry. Static linking on Windows embeds the three pillars into the single module \texttt{\_C.pyd} and keeps symbol visibility identical to the Linux shared-library layout without annotating every class.

\subsection{Product Layout: RPATH and the Two Preload Paths}
\label{sec:arch:rpath}

After \texttt{cmake --build}, the package tree is the product:

\begin{lstlisting}[caption={Post-build layout under \path{tensorplay/}.}, label=lst:layout]
tensorplay/
  lib/
    libp10.so
    libtpx.so
    libstax.so
    libtp_python.so
    cudart64_*.dll / cublas64_*.dll / cudnn*.dll   # Windows wheels only
  _C/
    __init__.so          # OUTPUT_NAME "__init__" :1176
    __init__.pyi
  __init__.py            # 1,197 lines, three dirty jobs
  _tensor.py             # Tensor = _C.TensorBase :12
  version.py             # generated at :330
\end{lstlisting}

The relative RPATH makes the layout relocatable. From \path{CMakeLists.txt:1200--1212}:

\begin{lstlisting}[caption={\path{CMakeLists.txt:1200--1212} --- RPATH is the loader contract.}, label=lst:rpath]
if(NOT WIN32)
    set_target_properties(p10 tpx stax PROPERTIES
        INSTALL_RPATH "$ORIGIN"
        BUILD_RPATH "$ORIGIN"
    )
    set_target_properties(tp_python PROPERTIES
        INSTALL_RPATH "$ORIGIN"
        BUILD_RPATH "$ORIGIN"
    )
    set_target_properties(_C PROPERTIES
        INSTALL_RPATH "$ORIGIN/../lib"
        BUILD_RPATH "$ORIGIN/../lib"
    )
endif()
\end{lstlisting}

\path{p10}, \path{tpx}, \path{stax}, and \path{tp_python} reside together in \path{tensorplay/lib}, so \texttt{\$ORIGIN} suffices: each finds its siblings without an absolute path. \path{_C} lives one directory deeper in \path{tensorplay/\_C}, so it uses \path{\$ORIGIN/../lib}. Verification is a single command with no Python involved:

\begin{lstlisting}[caption={Linux loader verification without importing Python.}, label=lst:readelf]
readelf -d tensorplay/lib/libp10.so | grep -i rpath      # $ORIGIN
readelf -d tensorplay/lib/libtpx.so | grep -i rpath      # $ORIGIN
readelf -d tensorplay/_C/__init__.so | grep -i rpath     # $ORIGIN/../lib
ldd tensorplay/_C/__init__.so | grep "not found"          # must be empty
\end{lstlisting}

Failure without this block manifests as \path{ImportError: libp10.so: cannot open shared object file} when the wheel is installed into a virtual environment whose \texttt{LD\_LIBRARY\_PATH} is empty, which is precisely the target scenario for a wheel. The comment at \path{CMakeLists.txt:1195--1199} documents this as the single reason RPATH exists; Windows ignores RPATH entirely, so the Windows branch is guarded by \texttt{if(NOT WIN32)}.

Windows uses explicit preload instead. \path{tensorplay/\_\_init\_\_.py:34--135} defines \path{\_load\_dll\_libraries()} guarded by \path{sys.platform == 'win32'}:

\begin{lstlisting}[caption={\path{tensorplay/\_\_init\_\_.py:72--133} --- ordered DLL preload on Windows.}, label=lst:winpreload]
kernel32 = ctypes.WinDLL("kernel32.dll", use_last_error=True)
# MKL -> CUDA/cuDNN -> p10/tpx/stax   :80
mkl_dlls = glob.glob(os.path.join(package_lib_path, "mkl_*.dll"))
cuda_dlls = glob.glob(os.path.join(package_lib_path, "cudart*.dll")) + \
            glob.glob(os.path.join(package_lib_path, "cublas*.dll")) + \
            glob.glob(os.path.join(package_lib_path, "cudnn*.dll"))
core_dlls = [os.path.join(package_lib_path, "p10.dll"),
             os.path.join(package_lib_path, "tpx.dll"),
             os.path.join(package_lib_path, "stax.dll")]
for dll in sorted_mkl + cuda_dlls + core_dlls:
    if with_load_library_flags:
        res = kernel32.LoadLibraryExW(dll, None, 0x00001100)  # :122
    else:
        res = kernel32.LoadLibraryW(dll)
\end{lstlisting}

\texttt{0x00001100} is \path{LOAD\_LIBRARY\_SEARCH\_DEFAULT\_DIRS | LOAD\_LIBRARY\_SEARCH\_DLL\_LOAD\_DIR}, the minimally permissive flag that still searches the package lib directory added earlier via \path{os.add\_dll\_directory} at \path{\_\_init\_\_.py:40--69}. Order is load-bearing: \texttt{mkl\_core} and \texttt{mkl\_sequential} are sorted first inside the MKL group at lines~85--94 because \texttt{mkl\_def} and \texttt{mkl\_avx2} depend on them; CUDA runtime is loaded before \path{p10} so that \texttt{CUDA::cudart} symbols required by p10's CUDA kernels are already resolved. The helper \path{\_add\_dll\_directory} tries both \path{tensorplay/lib} and the legacy \path{tensorplay/} root, plus the interpreter's \path{Library/bin}, the base environment, and the user site-packages bin, each guarded by \texttt{os.path.exists} so a missing Conda installation does not error.

On Linux the counterpart does not eagerly load anything in a CPU-only environment. \path{tensorplay/\_\_init\_\_.py:143--205} wraps the extension import:

\begin{lstlisting}[caption={\path{tensorplay/\_\_init\_\_.py:143--205} --- Linux CUDA wheel probing.}, label=lst:linuxpreload]
try:
    from . import _C as _C                                          # :199
except (ImportError, OSError) as _load_error:                         # :200
    if sys.platform.startswith('linux') and '_preload_cuda_deps' in globals():
        _preload_cuda_deps(_load_error)                              # :202
        from . import _C as _C                                       # :203
    else:
        raise

def _preload_cuda_deps(err=None):                                     # :174
    cuda_error = any(token in str(err) for token in
                     ('libcud', 'libcublas', 'libcurand', 'libnvrtc'))  # :177
    if not cuda_error:
        raise err
    for lib_folder, lib_name, required in (                           # :185
        ('cublas', 'libcublasLt.so.*[0-9]', True),
        ('cublas', 'libcublas.so.*[0-9]', True),
        ('cudnn',  'libcudnn.so.*[0-9]', True),
        ('cuda_nvrtc', 'libnvrtc.so.*[0-9]', False),
        ('cuda_runtime','libcudart.so.*[0-9]', True),
        ('curand', 'libcurand.so.*[0-9]', True),
    ):
        _preload_cuda_lib(lib_folder, lib_name, required=required)   # :193
\end{lstlisting}

\path{\_get\_cuda\_dep\_paths} at line~144 probes \path{nvidia/cublas/lib/libcublasLt.so.*} and \path{nvidia/cuda\_runtime/lib/libcudart.so.*} inside every \texttt{sys.path} entry, which is exactly the layout installed by the pip wheels \texttt{nvidia-cublas-cu*} and \path{nvidia-cuda-runtime-cu*}. If probing fails it falls back to \path{tensorplay/lib/libcublasLt.so.*}, the path used when the toolkit is bundled via \path{CMakeLists.txt:190--215}. \path{\_preload\_cuda\_lib:161} then does \path{ctypes.CDLL(candidates[0])}, which loads the SONAME before the extension's \texttt{DT\_NEEDED} is resolved, working around the common case where the user installed CUDA wheels into the environment's \texttt{site-packages} without setting \texttt{LD\_LIBRARY\_PATH}. Only errors mentioning \texttt{libcud}, \texttt{libcublas}, \texttt{libcurand}, or \texttt{libnvrtc} are intercepted; all other \texttt{ImportError} causes are re-raised unchanged.

\subsection{Virtual-Interface Decoupling: the USB Slot}
\label{sec:arch:usb}

\path{p10/include/TensorImpl.h:43} cannot include \path{tpx} yet must carry the differentiation state for tensors that require grad. The naive alternatives are both rejected: putting concrete fields (\texttt{grad\_fn\_}, \texttt{grad\_}) into \path{p10} couples storage to differentiation; letting \path{p10} include a \path{tpx} header creates a circular dependency that \texttt{cmake --build} cannot topologically sort and that defeats incremental builds. The design instead declares a pure abstract slot in \path{p10} and plugs a concrete object from \path{tpx} through \path{shared\_ptr<AutogradMetaBase>} and a \texttt{static\_cast} handshake.

At \path{p10/include/AutogradMetaBase.h:13--25} the slot is four operations, each pure virtual:

\begin{lstlisting}[caption={\path{p10/include/AutogradMetaBase.h:13--25} --- the pure interface.}, label=lst:autogradbase2]
class P10_API AutogradMetaBase {
public:
  virtual ~AutogradMetaBase() = default;
  virtual bool requires_grad() const = 0;
  virtual void set_requires_grad(bool) = 0;
  virtual Tensor grad() const = 0;
  virtual void set_grad(const Tensor&) = 0;
  virtual bool retains_grad() const = 0;
  virtual void set_retains_grad(bool) = 0;
};
\end{lstlisting}

The header includes only \texttt{Macros.h}; it forwards \texttt{class Tensor} without including \texttt{Tensor.h}, so the compile-time footprint is a single vtable plus six virtual slots (48 bytes on x86-64). No kernel, no engine, no graph concept crosses the boundary here.

\path{p10/include/TensorImpl.h:43--46} holds the slot:

\begin{lstlisting}[caption={\path{p10/include/TensorImpl.h:43--46} --- never-copied owner.}, label=lst:implslot]
  // Autograd extension point.
  // Never copied by TensorImpl copy operations: copies start without history.
  std::shared_ptr<AutogradMetaBase> autograd_meta_;
\end{lstlisting}

The copy constructor at \path{p10/src/TensorImpl.cpp:77--92} deliberately omits this member:

\begin{lstlisting}[caption={\path{p10/src/TensorImpl.cpp:77--92} --- history is not duplicated.}, label=lst:copyctor]
TensorImpl::TensorImpl(const TensorImpl& other)
    : storage_offset_(other.storage_offset_),
      sizes_and_strides_(other.sizes_and_strides_),
      dtype_(other.dtype_),
      device_(other.device_),
      version_counter_(other.version_counter_),
      inference_tensor_(other.inference_tensor_),
      is_contiguous_(other.is_contiguous_),
      memory_format_(other.memory_format_),
      storage_(other.storage_),
      shared_state_(other.shared_state_),
      sparse_state_(other.sparse_state_),
      transform_value_(other.transform_value_),
      transform_batch_dim_(other.transform_batch_dim_),
      transform_level_(other.transform_level_),
      quantizer_(other.quantizer_) {}
      // autograd_meta_ is intentionally absent: default-initialized to nullptr
\end{lstlisting}

Thus \texttt{Tensor b = a;} shares storage, sizes, strides, device, dtype, sparse state, quantizer, and the version counter alias, but not the graph. The invariant is: shape mutation and storage aliasing propagate; history does not. Move operations are defaulted, and \path{copy_metadata_from} at \path{TensorImpl.cpp:107} preserves the preservation of \path{autograd_meta_} by omission.
This matches the ``never copied'' contract at \path{TensorImpl.h:44} and enables \texttt{auto y = x + 1; y.backward()} where \texttt{x} stays a leaf and \texttt{y} becomes its child without aliasing metadata.

The concrete plug lives in \path{tpx/include/AutogradMeta.h:26--108}:

\begin{lstlisting}[caption={\path{tpx/include/AutogradMeta.h:26--47} --- concrete fields, tpx only.}, label=lst:autogradconcrete]
class TENSORPLAY_API AutogradMeta : public AutogradMetaBase {
private:
  bool requires_grad_ = false;
  bool retains_grad_ = false;
  tensorplay::Tensor grad_;
  std::shared_ptr<Node> grad_fn_;
  std::weak_ptr<Node> grad_accumulator_; // avoids leaf cycle
  uint32_t output_nr_ = 0;
  bool has_view_info_ = false;
  tensorplay::Tensor view_base_;
  std::vector<int64_t> view_sizes_;
  std::vector<int64_t> view_strides_;
  int64_t view_storage_offset_ = 0;
  std::function<tensorplay::Tensor(const tensorplay::Tensor&)> view_fn_;
  mutable std::mutex view_mutex_;
};
\end{lstlisting}

\texttt{grad\_accumulator\_} is \texttt{weak\_ptr<Node>} rather than \texttt{shared\_ptr<Node>} because \texttt{AccumulateGrad} strongly owns its leaf tensor; a strong back edge would form an uncollectable cycle that leaks every leaf that ever participated in a graph. All other members are owned strongly; \texttt{view\_fn\_} plus \texttt{view\_mutex\_} support stale-view replay at \path{tpx/src/Autograd.cpp:34--79}.

The handshake is the two helpers at \path{tpx/src/Autograd.cpp:15--32}, each a single \texttt{static\_cast} with no \texttt{dynamic\_cast} on the hot path:

\begin{lstlisting}[caption={\path{tpx/src/Autograd.cpp:15--32} --- the cast boundary.}, label=lst:handshake]
AutogradMeta* get_autograd_meta(const Tensor& t) {
    if (auto* impl = t.unsafeGetTensorImpl().get()) {
        return static_cast<AutogradMeta*>(impl->autograd_meta()); // :17
    }
    return nullptr;
}
AutogradMeta* get_or_create_autograd_meta(const Tensor& t) {
    auto impl = t.unsafeGetTensorImpl();
    if (!impl) return nullptr;
    if (auto* meta = impl->autograd_meta()) {
        return static_cast<AutogradMeta*>(meta);                  // :26
    }
    auto meta = std::make_shared<AutogradMeta>();
    auto* raw = meta.get();
    impl->set_autograd_meta(std::move(meta));                      // :30
    return raw;
}
\end{lstlisting}

The call at line~17 is safe because the only concrete subclass ever assigned to \texttt{autograd\_meta\_} is \texttt{AutogradMeta}, constructed at line~28 and installed at line~30. No header in \path{p10} ever sees \texttt{AutogradMeta.h}, so \path{p10/CMakeLists.txt} never lists \path{tpx/include}. The static type system plus the shared-library boundary together enforce the invariant; the link-time proof is:

\begin{lstlisting}[caption={Acyclicity proof: no text match for \path{tpx} inside \path{p10} public headers.}, label=lst:acyclicgrep]
grep -rn "tpx" p10/include/ --include="*.h" | wc -l   # expected: 0
grep -rn "AutogradMeta" p10/ --include="*.h" | grep -v AutogradMetaBase
# expected: only TensorImpl.h:43 shared_ptr<AutogradMetaBase>
\end{lstlisting}

A second proof is the failed build when the cast target changes: if \path{tpx} were to rename \texttt{AutogradMeta} without updating the cast, the extension \path{_C} would fail to link with \path{undefined reference to tensorplay::tpx::AutogradMeta} rather than corrupting a tensor at runtime.

The per-call cost of this design is one indirect virtual call for \texttt{requires\_grad()} / \texttt{grad()} / \texttt{set\_grad()} plus one pointer indirection for \texttt{autograd\_meta\_}. The benefit is that \path{p10} rebuilds when a kernel changes no longer trigger a rebuild of \path{tpx}, and \path{tpx} rebuilds when engine scheduling changes do not trigger a rebuild of \path{p10}.

\subsection{Design Axiom: Level Monotonicity}
\label{sec:arch:axiom}

Let $V=\{\path{p10},\path{tpx},\path{stax},\path{_C}\}$ and let $D\subseteq V\times V$ be the relation ``$a$ links $b$'' (i.e.\ $a$ has a \path{target\_link\_libraries} edge to $b$). Define \texttt{level}: $V\rightarrow \mathbb{N}$ by

\begin{table}[H]
\centering
\caption{Levels are total and equal the \texttt{add\_subdirectory} order at \path{CMakeLists.txt:938--944}.}
\label{tab:levels}
\small
\begin{tabular}{clcl}
\toprule
Level & Target & \texttt{add\_subdirectory} line & Header import allowed from higher \\
\midrule
0 & \path{p10} & \path{CMakeLists.txt:939} & No lower target exists \\
1 & \path{tpx} & \path{CMakeLists.txt:941} & May include \path{p10/include/*.h} \\
2 & \path{stax} & \path{CMakeLists.txt:944} & May include \path{p10/include}, \path{tpx/include} \\
3 & \path{_C} / \path{tp_python} & \path{CMakeLists.txt:954}, \texttt{1106} & May include \path{p10}, \path{tpx}, \path{stax} \\
\bottomrule
\end{tabular}
\end{table}

Axiom (level monotonic): $\forall (a,b)\in D,\; \texttt{level}(a) > \texttt{level}(b)$.

Equivalently, every edge points strictly downward in the order \path{p10=0 < tpx=1 < stax=2 < \_C=3}. Table~\ref{tab:levels} shows that \texttt{D} contains only \texttt{(tpx,p10)}, \texttt{(stax,p10)}, \texttt{(stax,tpx)}, \texttt{(tp\_python,p10)}, \texttt{(\_C,p10)}, \texttt{(\_C,tpx)}, \texttt{(\_C,stax)}, \texttt{(\_C,tp\_python)}, each satisfying the strict inequality. No pair with \texttt{level}(a) $\le$ \texttt{level}(b) is present; in particular \texttt{(p10,tpx)} and \texttt{(p10,stax)} are absent.

The enforcement is by the linker, not by convention. Adding \path{\#include "tpx/AutogradMeta.h"} inside any \path{p10/include/Tensor*.h} introduces a reference to \path{tensorplay::tpx::AutogradMeta::requires\_grad()} whose definition lives in \path{libtpx.so}. Because \path{p10} does not link \path{tpx} (and must not, by the axiom), the link of \path{libp10.so} succeeds but the link of any consumer that does link \path{p10} alone fails with \path{undefined reference to tensorplay::tpx::AutogradMeta}. On Linux this is diagnosed during \texttt{cmake --build}; on Windows it is diagnosed at the \texttt{link.exe} step for \texttt{\_C.pyd}. The alternative failure mode for a conventional monolithic framework would be a static-initialization order defect diagnosed only at program startup.

The axiom also determines rebuild granularity. Touching \path{p10/src/backend/cpu/ActivationKernels.cpp} dirties only \path{p10} and the final link of \path{_C}; \path{tpx} and \path{stax} are not rebuilt because they do not depend on \path{p10} sources, only on its installed headers. Touching \path{tpx/src/Engine.cpp} rebuilds \path{tpx} and relinks \path{stax} and \path{_C} but not \path{p10}. This is verified by comparing mtimes after a no-op edit:

\begin{lstlisting}[caption={Granularity check: only downward consumers relink.}, label=lst:granularity]
touch p10/src/backend/cpu/ActivationKernels.cpp && cmake --build build --target p10 -j4
ls -lt tensorplay/lib/libp10.so tensorplay/lib/libtpx.so tensorplay/lib/libstax.so
# expected: libp10.so newest, others older

touch tpx/src/Engine.cpp && cmake --build build --target tpx -j4
ls -lt tensorplay/lib/libtpx.so tensorplay/lib/libstax.so tensorplay/_C/__init__.so
# expected: libtpx.so newest among the three; libp10.so unchanged
\end{lstlisting}

A corollary concerns \path{tp_python}. At \path{CMakeLists.txt:954--961} it is a \texttt{SHARED} library \path{src/bindings/python/CPythonBridge.cpp} that links only \path{p10} and \texttt{pybind11}. It exists for exactly one reason documented at \path{CMakeLists.txt:946--953}: the pybind11 caster substrate and the wrap-identity cache must be registered from a single module boundary. If \texttt{CPythonBridge.cpp} were compiled separately inside \path{p10} and inside \path{_C}, each copy would carry its own registry and the first \texttt{Tensor} returned to Python would segfault. The single shared copy at level~3 keeps \path{level(tp\_python)=3 > level(p10)=0} and still allows out-of-tree op modules to link the same substrate via \texttt{add\_tensorplay\_op} without recompiling the core.

\subsection{Python Veneer: Three Dirty Jobs in 1,197 Lines}
\label{sec:veneer}

\path{tensorplay/\_\_init\_\_.py} is 1,197 lines and, together with \path{tensorplay/\_tensor.py}, constitutes the entire Python-level design that the compiled extension cannot express. Every other Python module (\texttt{nn}, \texttt{optim}, \texttt{autograd}, \texttt{functional}, \texttt{distributed}) ultimately re-enters \path{_C}. Three concerns are impossible to implement cleanly in C++ and are therefore concentrated here.

\subsubsection{Job 1: DLL / Shared-Object Preload (lines 34--205)}
Described in \S\ref{sec:arch:rpath}, this job handles the divergence between the Linux loader (which respects \texttt{RPATH}) and the Windows loader (which ignores it). On Windows the job is mandatory; on Linux it is an opportunistic repair for CUDA wheels. The code is split at line~34 (\path{if sys.platform == 'win32'}) and line~143 (\path{elif sys.platform.startswith('linux')}) with no overlap, so a reader can audit one platform without understanding the other. The job is the only place that imports \texttt{ctypes} and \texttt{glob}; no kernel or engine file references either.

\subsubsection{Job 2: Symbol Renaming (\texttt{\_C.add} $\rightarrow$ \texttt{tensorplay.add})}

The extension exports every operator as \texttt{\_C.add}, \texttt{\_C.relu}, \texttt{\_C.conv2d} at their C++ names. The veneer re-exports them as flat \texttt{tensorplay.*} names and rewrites \texttt{\_\_module\_\_} so tracebacks and \path{help(tensorplay.add)} report the public location. The loop at \path{tensorplay/\_\_init\_\_.py:408--443} is:

\begin{lstlisting}[caption={\path{tensorplay/\_\_init\_\_.py:408--443} --- renaming with builtin fallback.}, label=lst:renaming]
__attr_name, __obj = "", None
for __attr_name in dir(_C):
    if __attr_name[0] != "_" and not __attr_name.endswith("Base"):
        __all__.append(__attr_name)
        __obj = getattr(_C, __attr_name)
        if callable(__obj) or inspect.isclass(__obj):
            if os.getenv("TENSORPLAY_BUILDING_STUBS") == "1":
                continue
            if __obj.__module__ != __name__:
                try:
                    __obj.__module__ = __name__          # pybind11 class: succeeds
                except AttributeError:                    # builtin_function_or_method: fails
                    if callable(__obj):
                        def make_wrapper(f):
                            @functools.wraps(f)
                            def wrapper(*args, **kwargs):
                                return f(*args, **kwargs)
                            wrapper.__module__ = __name__
                            return wrapper
                        wrapper = make_wrapper(__obj)
                        if __attr_name in globals():
                            globals()[__attr_name] = wrapper
            if __attr_name not in globals():
                globals()[__attr_name] = __obj
\end{lstlisting}

The \path{try/except} exists because pybind11 functions are \path{builtin\_function\_or\_method} descriptors whose \texttt{\_\_module\_\_} attribute is read-only in CPython; the fallback wrapper preserves \texttt{inspect.signature} via \texttt{functools.wraps} while fixing \texttt{\_\_module\_\_} to \texttt{"tensorplay"}. Without this job, users would call \texttt{tensorplay.\_C.add} or see tracebacks mentioning \texttt{tensorplay.\_C} instead of \texttt{tensorplay}.

The tensor type itself is finished here: \path{tensorplay/\_tensor.py:12} defines \path{Tensor = \_C.TensorBase} and then attaches methods (\texttt{t}, \texttt{type}, \texttt{cuda}, \texttt{cpu}, \texttt{long}, \texttt{float}, plus hooks, bitwise dunders, \texttt{permute}, \texttt{expand}, \texttt{unique}, \texttt{topk}) onto that alias. The C++ binding at \path{src/bindings/python/Tensor.cpp} uses \texttt{py::dynamic\_attr()} on \texttt{TensorBase} so Python subclasses like \path{class MyTensor(Tensor)} can attach per-instance attributes while still being recognized by the native caster. The check is \path{py::isinstance< Tensor >(obj)} via the shared caster in \path{tp_python}.

\subsubsection{Job 3: Lazy Subpackages via \texttt{\_\_getattr\_\_} (lines 1118--1134)}

A direct \path{import tensorplay.linalg} at veneer top level would force importing 354 modules on every \texttt{import tensorplay}, adding hundreds of milliseconds on import even for scripts that only use \path{tensorplay.tensor([1])}. Instead the veneer registers a lazy set:

\begin{lstlisting}[caption={\path{tensorplay/\_\_init\_\_.py:1118--1134} --- lazy subpackages.}, label=lst:lazy]
else:
    _lazy_modules = {
        "audio",
        "export",
        "func",
        "fft",
        "linalg",
        "quantization",
        "sparse",
        "special",
        "vision",
    }
    def __getattr__(name):
        if name in _lazy_modules:
            return importlib.import_module(f".{name}", __name__)
        raise AttributeError(f"module '{__name__}' has no attribute '{name}'")
\end{lstlisting}

\texttt{\_\_getattr\_\_} is the module-level hook introduced in Python~3.7. It is only invoked for missing attributes, so known names like \texttt{tensorplay.Tensor} or \texttt{tensorplay.add} never enter this path. Under \texttt{TYPE\_CHECKING} (true for static analysis only, false at runtime) the veneer instead imports \texttt{export} and \texttt{func} eagerly at lines~1108--1115 so that pylance and other LSP servers resolve attributes without executing the lazy hook. The accompanying \texttt{TYPE\_CHECKING} import is guarded by \texttt{if TYPE\_CHECKING:} and has no runtime cost.

Together these three jobs are the only Python-side complexity with cross-cutting impact. Everything else in \path{tensorplay/\_\_init\_\_.py} is declarative: \texttt{DType} aliases at lines~230--259, \texttt{MemoryFormat} / \texttt{Layout} / \texttt{QScheme} enumerations at lines~264--305, \texttt{max}/\texttt{min}/\texttt{gradient} wrappers at lines~1038--1075, and the \texttt{\_\_all\_\_} extension at lines~336--369 that enumerates 550+ operators with a sorted contract.

\subsection{Stax: Minimal IR That Is Not a Second Frontend}
\label{sec:arch:stax}

\path{stax} is 76 lines of CMake at \path{stax/CMakeLists.txt:1--41} producing \path{libstax.so} from \path{stax/src/*.cpp}. Its public surface is two headers: \path{stax/include/Graph.h:1--137} and \path{stax/include/Fusion.h:1--76}. The design note at \path{tensorplay/stax.py:1--7} is explicit:

\begin{lstlisting}[caption={\path{tensorplay/stax.py:1--7} --- not a second frontend.}, label=lst:staxpy]
"""Stax backend namespace.
Stax is not a second public compiler frontend.  Use ``tensorplay.compile``
and select ``backend="stax"`` once the backend has a production lowering.
The native ``tensorplay._C._stax`` module remains available for low-level IR
and optimizer development.
"""
from ._stax.stax import stax
\end{lstlisting}

\path{Graph.h:47--60} defines a \texttt{ValueNode} as ``producer plus slot'':

\begin{lstlisting}[caption={\path{stax/include/Graph.h:47--60} --- values are slots.}, label=lst:valuenode]
struct STAX_API ValueNode {
    size_t id;
    OpNode* producer; // Producer op, nullptr for graph inputs
    size_t producer_output_index; // Output index of producer
    std::string dtype = "float32";
    std::vector<int64_t> shape;
    std::string device = "cpu";
    std::vector<OpNode*> uses;
    ValueNode(size_t id_, OpNode* n, size_t off) : id(id_), producer(n), producer_output_index(off) {}
};
\end{lstlisting}

\texttt{OpNode} at \path{Graph.h:69--87} groups inputs, outputs, owning graph, and attributes through a \path{variant<int64\_t, double, string, vector<int64\_t>, vector<double>>} map at line~62. \texttt{Graph} at \path{Graph.h:89--105} owns the \texttt{nodes} and \texttt{values} vectors plus the \texttt{inputs} / \texttt{outputs} boundaries, with helpers \texttt{addInput}, \texttt{createNode}, and \texttt{registerOutput} at lines~95--97. The \texttt{IRBuilder} helper at \path{Graph.h:107--123} creates named nodes and propagates dtype from the first input.

Execution is strictly sequential at \path{stax/src/Graph.cpp:179--761}. \texttt{Graph::execute} binds concrete \texttt{Tensor} arguments to \texttt{env[ input->id ]} at line~192, then iterates \texttt{nodes} in creation order. Each node dispatches to \texttt{tpx::ops} (e.g.\ \texttt{add}, \texttt{conv2d}, \texttt{matmul}, \texttt{max\_pool2d}, \texttt{batch\_norm}) via the regular dispatcher, preserving device and differentiation semantics. Intermediate lifetimes are bounded by \texttt{remaining\_uses} at line~198 and \texttt{keep\_alive} at line~199; dead values are cleared via \texttt{env[id]=Tensor()} at line~215, allowing the allocator to recycle storage inside a single graph run without retaining every intermediate until the function returns.

\path{Fusion.h:15--73} adds the only optimization: a pass infrastructure with a single registered pass that fuses \texttt{mul} followed by \texttt{add} into \texttt{fused\_mul\_add} (a single kernel in \path{p10}). The registry at \path{Fusion.h:23--51} is a \path{map<string, Creator>}, and \texttt{fuseGraph} at line~73 is retained for compatibility. There is no alias analysis, no layout propagation, no autotuning, no code generation to C++/CUDA/PTX, and no persistence format beyond the in-memory \texttt{Graph}.
