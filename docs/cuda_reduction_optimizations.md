# CUDA reduction 验证记录

本轮实现了 CUDA `hash_tensor` 的 XOR 归约、非对齐输入的头部与向量主体处理、连续输出分组，以及超出 64 个 iterator 维度的动态元数据。引擎修订号为 14。

连续输出按 vec4、vec2 或标量分派。归约长度小于 32768 时使用标量输出，以控制较短归约的调度与最终合并成本。输出分组只要求输入布局支持连续读取，投影后的输出仍按各自的实际 stride 写入。

大张量验证发现并修复了两处索引问题：拆分输出后，第二输出和累加缓冲需要同步调整地址；packed 极值状态在合并前需要把局部索引重定位到完整归约空间。相等值取首次出现的索引，NaN 优先且同样取首次出现的索引。

## 性能测量

设备为 RTX 3090。使用 CUDA event 测量 7 组、每组 100 次 C++ 归约启动的中位时间，单位为微秒。非对齐测试的输入偏移为 1 个元素；输出分组测试沿二维输入的第 0 轴求和。时间包括循环内启动和临时缓冲管理产生的间隔。

| 路径 | 输入 | 基线 | 改动后 | 时间变化 |
| --- | --- | ---: | ---: | ---: |
| 非对齐输入 | float32，64M 元素 | 318.657 | 309.954 | 减少 2.7% |
| 非对齐输入 | half→float32，64M 元素 | 172.993 | 157.727 | 减少 8.8% |
| 连续输出分组 | float32，1048576×16 | 93.060 | 85.699 | 减少 7.9% |
| 连续输出分组 | half→float32，1048576×16 | 66.787 | 48.946 | 减少 26.7% |
| 较短归约 | half→float32，16384×128 | 10.568 | 11.817 | 增加 11.8% |

非对齐路径的 1M 元素测试没有收益；half 测试由 6.646 增至 7.158 微秒。上述结果只代表这些 dtype 和布局，不代表所有归约都加速。

## 可重复验证

```bash
python3 -m pytest test/test_cuda_reductions.py test/test_cuda_fused_aminmax_varmean.py test/test_cuda_reduction_layouts.py test/test_cuda_hash_tensor.py -q
TP_TEST_LARGE_REDUCTIONS=1 python3 -m pytest test/test_cuda_large_reductions.py -q
```

大张量用例分别实际分配超过 2 GiB 的 int8 输入、约 4 GiB 的 int64 输入和超过 8 GiB 的 float32 输入，覆盖完整归约、输出地址拆分、输出分组、极值索引、相等值与 NaN。

普通 65/96/128 维输入中的单例轴会被 iterator 合并。`test_cuda_reduction_dimensions` 另外保留 70 个 iterator 维度，验证额外元数据的上传和设备端寻址，以及默认流和非默认流。配置 `BUILD_TESTS=ON` 后可通过 CTest 运行该目标；没有 CUDA 设备时返回跳过状态。

运行时生成归约代码暂未实现：目前没有测量证据表明它能带来额外收益，而运行时编译、缓存和依赖管理需要独立的实现与验证。

## 构建记录

最终构建使用单个 `ninja -C build -j6 _C` 和共享 sccache。大型 CUDA 文件的编译及汇编需要持续等待，未通过终止 ninja 缩短等待。

过程中 sccache 服务曾意外退出，客户端回退编译与旧孤儿编译同时指向同一对象文件。清理旧孤儿进程树并恢复服务后继续构建，随后定期查询统计维持服务活跃。

一次独立诊断程序因可执行文件路径与临时目录重名而链接失败，改名后通过。另一次诊断编译未及时避开共享构建，产物位于独立临时目录；后续正式构建均等待编译进程静默后启动。独立诊断链接使用了允许共享库未解析符号的选项，规避当前库中无关的两个 BLAS 符号；该选项没有加入正式构建配置。
